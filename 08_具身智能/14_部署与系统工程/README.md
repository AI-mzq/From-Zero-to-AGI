# 14_部署与系统工程

> 把感知、模型、规划和控制组合成满足实时性、稳定性与资源约束的机器人系统。

## 本章定位

红杯被人移动后，相机已经拍到新位置，机械臂却仍向旧位置靠近。模型可能读到了排队的旧画面，也可能新动作还在等待执行。部署需要把传感、推理、规划与控制连接起来，让数据和命令在有效时间内到达正确模块，并在异常时进入明确的处理流程。

本章按系统接口、运行时序、算力布局、故障处置与版本发布组织内容。机器人组件的共同概念见[机器人系统基础](../02_机器人系统基础/README.md)，安全与任务验收见[评测、安全与可靠性](../12_评测安全与可靠性/README.md)。

## 读完本章，你应该能够

- 描述观测、模型输出和控制命令在部署系统中的接口约定。
- 根据任务变化速度分析延迟、队列与多频率调度。
- 比较端侧和远程推理的资源、网络与故障条件。
- 用日志回放、分阶段测试和版本记录定位并验证系统改动。

<a id="interfaces"></a>

## 把模块连接成可检查的执行链

```text
传感器与本体状态 → 预处理与状态估计 → 策略或规划
→ 动作解码与约束检查 → 控制器与驱动 → 执行反馈
                   任务状态、监测与日志贯穿全链路
```

| 接口 | 至少说明什么 |
| --- | --- |
| 观测输入 | 图像布局、模态、时间戳、坐标系、标定和缺失处理 |
| 模型输出 | 动作表示、单位、归一化、预测步数与对应时间 |
| 执行命令 | 控制模式、目标有效期、命令标识、取消与覆盖方式 |
| 执行反馈 | 已接收、执行中、完成、失败以及实际状态 |
| 任务接口 | 当前阶段、成功判据、恢复入口和人工接管 |

抓杯策略输出末端增量时，需要先恢复单位和参考系，再按本体接口形成目标。动作块更新时，还要明确新目标覆盖哪些尚未执行的旧动作。一次命令已被服务接收，之后仍需通过执行反馈和任务状态判断其效果。

ROS 2 的 Topic 可承载连续状态流，Service 适合请求响应交互，Action 提供长任务的进度、结果和取消语义。驱动适配层负责把软件命令映射到设备接口。ros2_control 的控制器管理器组织硬件状态读取、控制器更新和命令写入，实际控制模式和周期需结合设备配置。[ros2_control Controller Manager](https://control.ros.org/rolling/doc/ros2_control/controller_manager/doc/userdoc.html)

<a id="timing"></a>

## 延迟预算从观测一直算到动作生效

端到端链路包括采集、传输、预处理、排队、推理、动作解码和控制生效。异步执行时部分阶段可以重叠，应通过时间戳追踪关键路径，并测量动作生效时所用观测的年龄。

例如，假设某次串行链路的采集传输为 20 ms、预处理与排队为 15 ms、推理为 60 ms、下发与生效为 15 ms，总计 110 ms。这组示例数值需要与杯子移动速度和任务容差一起判断。平均耗时之外，还应记录长尾延迟、抖动和错过截止时间的次数。实时计算关注任务能否在约定时间内完成。[ROS 2 实时系统背景](https://design.ros2.org/articles/realtime_background.html)

### 多频率与队列

相机采样、策略更新和底层控制可以使用不同频率。策略输出一段动作后，控制器在自己的周期内跟踪目标。推理耗时超过更新间隔时，需要决定跳过旧观测、缩短队列、降低输入负载或进入受控降级。

| 数据类型 | 队列与时效考虑 |
| --- | --- |
| 实时观测 | 根据同步需求读取足够新的数据，限制排队造成的陈旧 |
| 动作目标 | 检查有效期、执行时间和命令顺序，拒绝失效目标 |
| 任务事件 | 保留关键结果，并处理重复、重连与确认 |
| 日志 | 缓冲并监测写入压力，避免阻塞控制关键路径 |

通信的可靠传输、历史深度和有效期应按数据用途配置，并验证发布与订阅设置兼容。可靠传输可能增加重传和等待，消息送达后还需检查业务时效。[ROS 2 Quality of Service Policies](https://design.ros2.org/articles/qos.html)

<a id="inference"></a>

## 端侧、边缘与云端怎样分工？

| 布局 | 主要收益 | 需要验证 |
| --- | --- | --- |
| 机器人端侧 | 观测和动作链路短，可本地持续运行 | 算力、内存、功耗、散热和长期降频 |
| 局域网边缘服务器 | 共享较强计算资源 | 网络抖动、拥塞、多设备竞争和失联 |
| 远程云端 | 支持较大模型、集中管理和训练 | 往返延迟、可用性、数据传输与访问控制 |

可以把高层任务理解放在远端，在本地保留时效敏感的执行监督与底层控制。远端参与动作推理时，要给请求和返回动作绑定观测时间、任务实例和有效期。网络断开后的行为需根据本体、持物和接触状态设计并验证。

### 推理优化如何验收？

量化、蒸馏、算子融合和低精度执行可以改变内存或计算成本，实际收益取决于硬件与运行时。还可调整图像分辨率、观测窗口和生成迭代步数。每项改动都应同时检查闭环任务结果，例如量化后夹爪的小幅纠偏是否仍有足够精度。

测试应包含预热后的持续运行、热状态、多任务负载和传感输入变化。固定模型版本、输入约定与硬件条件，分别比较峰值内存、功耗、延迟分布、任务成功率和恢复表现。模型部署的通用方法见[大模型推理与部署](../../09_大模型推理与部署/README.md)。

<a id="recovery"></a>

## 启动、故障和恢复怎样管理？

启动时先确认设备、标定和控制模式，再准备模型服务，完成输入输出检查后允许执行。ROS 2 生命周期节点提供配置、激活、停用等状态，可用于组织这些阶段。系统还需检查硬件和服务实际是否就绪。[ROS 2 Managed Nodes](https://design.ros2.org/articles/node_lifecycle.html)

| 故障 | 处理时应确认 |
| --- | --- |
| 模型超时或服务失联 | 当前动作是否仍有效，执行端是否需要停止或进入已验证的保持状态 |
| 传感数据缺失或过期 | 是否能获得有效状态，能否继续当前阶段 |
| 重复请求或重连 | 命令是否已执行，任务实例是否已变化 |
| 控制或硬件异常 | 驱动状态、接触与负载，停止流程及人工处置入口 |
| 模块重启 | 旧命令和旧推理结果是否已失效，当前任务是否仍可恢复 |

夹爪闭合等物理动作重试前，要核查执行状态。使用命令标识可以辅助去重，跨进程重启还需设计状态持久化或重新确认机制。切换到人工控制时应明确当前控制权，恢复自动执行前重新读取本体与任务状态。

<a id="observability"></a>

## 怎样用日志与回放找到问题？

为一次任务关联任务 ID、观测时间、推理请求、动作块、命令和反馈。运行指标包括观测年龄、队列深度、超时、命令拒绝、跟踪误差、温度、内存和任务结果。异常前后的片段可用环形缓冲保存，记录丢失和采集开销也需要监测。

rosbag2 可记录与回放 ROS 2 通信，便于检查同一时段的状态和消息。回放感知输入适合比较模型或预处理结果，闭环行为还会受到新动作和环境响应影响。物理命令回放应使用隔离的测试路径，并在仿真或专门评估过的条件下进行。[rosbag2 官方仓库](https://github.com/ros2/rosbag2)

红杯移位后仍抓向旧位置时，可以依次查相机时间、模型实际读取的帧、推理结束时刻、新旧动作切换和执行反馈。这样能确定是观测积压、模型判断还是命令队列导致偏差。

<a id="release"></a>

## 怎样发布并验证一个部署版本？

1. **固定完整配置。** 记录模型、预处理、动作统计量、标定、机器人描述、控制参数、驱动与运行时版本，以及适用硬件。
2. **检查离线接口。** 用已知观测核对解码、维度、单位、坐标和时间语义。
3. **完成仿真与回放验证。** 检查正常链路以及超时、丢帧和失联的处理。
4. **逐步验证真机。** 从低风险范围扩展到完整任务，比较成功率、延迟、异常事件和人工投入。
5. **准备成套回退。** 回退模型时同步恢复相容的配置和接口约定，确认机器人当前状态允许切换后再恢复任务。

容器和依赖锁定有助于重建软件环境，设备固件、内核、驱动和标定也要进入版本记录。发布后仍应持续检查温度、数据新鲜度和任务结果，发现退化后保留证据，再回到对应模块定位。

## 自检问题

1. 模型推理很快，为什么动作仍可能使用过期观测？
2. 新动作块返回时，需要怎样处理旧动作和超时结果？
3. 通信重连后，为什么不能直接重复上次物理命令？
4. 模型回退时还应恢复和核对哪些配置？

<details>
<summary>展开参考答案</summary>

1. 采集、传输、队列和执行都可能增加观测年龄，应测量完整链路的时间。
2. 核对任务实例、时间索引和有效期，再按约定取消或覆盖尚未执行的部分。
3. 命令可能已经生效，且身体或对象状态可能变化。需要查执行反馈并重新确认当前状态。
4. 核对预处理、动作归一化、标定、控制模式、驱动与运行时兼容性，并确认当前机器人状态。
