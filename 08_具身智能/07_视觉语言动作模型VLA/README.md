# 07_视觉语言动作模型 VLA

> 从“把红杯放进托盘”出发，看视觉、语言和机器人状态怎样共同决定动作。

## 本章定位

第 06 章讨论策略如何生成并执行一段动作。本章加入一个条件：“把红杯放进左边的托盘。”桌面上有两个杯子和两个托盘，机器人既要依据语言选对对象和目的地，也要根据视角、夹爪位置和执行反馈调整动作。**视觉语言动作模型（Vision-Language-Action Model，VLA）学习的是从视觉观测和语言条件到机器人动作的映射**，也可以接入关节状态等本体观测。

## 读完本章，你应该能够

- 从任务中找出语言、视觉和本体状态分别提供的信息。
- 比较不同 VLA 如何复用视觉语言能力、输出动作并对接控制器。
- 根据目标本体和任务数据判断预训练模型需要怎样适配。
- 设计测试，区分语言理解、动作执行和跨本体迁移的表现。

<a id="inputs"></a>

## 视觉、语言和本体状态分别提供什么？

语言指定目标和约束，例如「红杯」「左边的托盘」「保持杯口朝上」。视觉提供参照物、空间布局、遮挡和目标变化。本体观测提供关节状态、末端位姿或夹爪开合等信息。同一画面配上「拿蓝杯」时，动作应该随指令改变。同一条指令遇到红杯换位置时，动作应该随观测改变。

| 系统 | 典型输出 | 在抓杯任务里的作用 |
| --- | --- | --- |
| 视觉语言模型（VLM） | 文本、语义描述或定位信息 | 判断哪个是红杯，哪个托盘在左边 |
| 视觉运动策略 | 动作或动作块 | 根据观测完成抓取，可由固定目标或任务 ID 指定技能 |
| 视觉语言动作模型（VLA） | 由视觉和语言共同决定的动作或动作块 | 按当前指令选择对象，并结合观测执行操作 |

普通 VLM 可以参与高层规划并调用已有技能。VLA 的动作输出则需要通过示范、交互或其他动作监督与具体本体建立联系。某种杯子的语义知识可以帮助选对目标，夹持力度、接近方向和滑动后的调整仍取决于机器人数据和执行反馈。

<a id="architecture"></a>

## 视觉语言条件怎样传到动作输出端？

```text
相机观测 + 任务指令 + 可选本体状态
→ 条件编码与融合 → 动作预测 → 动作解码与控制
←─────────────── 读取执行后的新观测
```

视觉编码器将画面转成特征，语言编码器或多模态骨干提供任务条件。输出端可以沿用序列解码，把动作映射为离散 Token，也可以由专门的动作头生成连续动作。动作专家通常指负责动作预测的模块，其输入和参数共享方式依模型而变。动作 Token 的粒度、连续动作的坐标系和动作块的执行长度都需要结合第 06 章的接口来看。

| 代表工作 | 适合用来理解的问题 |
| --- | --- |
| [RT-1](https://arxiv.org/abs/2212.06817) | 在真实机器人示范上规模化训练指令条件策略，输出离散化控制量 |
| [RT-2](https://arxiv.org/abs/2307.15818) | 将动作编码成序列输出，在机器人轨迹与视觉语言任务上联合微调 |
| [Open X-Embodiment 与 RT-X](https://arxiv.org/abs/2310.08864) | 汇集多本体数据，并用 RT-X 实验检验跨数据集训练的迁移收益 |
| [Octo](https://arxiv.org/abs/2405.12213) | 用模块化输入和扩散动作头训练通用策略，再适配新的观测和动作空间 |
| [OpenVLA](https://arxiv.org/abs/2406.09246) | 在开放的视觉语言骨干上训练离散动作输出，并研究目标任务微调 |
| [π₀](https://arxiv.org/abs/2410.24164) | 结合视觉语言骨干与动作专家，用 Flow Matching 生成连续动作块 |
| [GR00T N1](https://arxiv.org/abs/2503.14734) | 面向通用人形机器人结合视觉语言理解与连续动作生成，并引入不同来源的训练数据 |

语言规划器负责拆解任务和选择子目标时，底层 VLA 可以按子指令执行抓取、搬运或放置。分层系统还需要定义何时切换子目标、如何确认完成，以及失败后由谁恢复。动作专家负责生成动作，任务分层负责组织技能，两者可以同时出现在同一系统中。

<a id="training"></a>

## 训练数据怎样变成目标本体上的技能？

1. **获得语义表征。** 可以从已有 VLM 初始化，也可以组合预训练视觉和语言编码器。图文数据帮助建立对象、属性和语言之间的联系。
2. **用机器人轨迹建立动作监督。** 将指令、相机观测、本体状态和示范动作按执行时序对应起来。离散输出通常预测动作 Token，连续生成头使用与其机制相应的训练目标。
3. **对齐多来源数据。** 数据集混合前应核对单位、坐标系、控制频率、夹爪语义和缺失字段。外观相似的两台机械臂可能具有不同的末端接口。共享动作空间、本体条件或专用输入输出层都可用于处理差异。
4. **在目标机器人上适配并验证。** 根据数据量和接口差异，选择调整动作头、参数高效微调或更全面的微调。把目标本体上的演示覆盖、执行结果和失败轨迹一起用于判断适配是否有效。

如果训练集中每次都抓靠左的杯子，即使每条示范都附了「抓红杯」，策略也可能从位置猜答案。让红蓝杯在不同位置交替出现，并记录同一布局下不同指令对应的动作，有助于模型学到语言真正约束了什么。跨本体数据也应检查任务和环境是否重叠，否则很难判断性能变化究竟来自本体迁移还是场景分布变化。

<a id="execution"></a>

## 动作如何在机器人上闭环执行？

部署时先将观测与指令送入模型，将动作输出解码并恢复为控制接口需要的单位和参考系。底层控制器跟踪动作目标，系统根据新观测、接触反馈或任务状态判断是否继续。策略预测的步数与实际执行步数可以不同，尤其在接近接触或遮挡突然变化时，旧动作块的有效时间会缩短。

| 阶段 | 红杯任务中的执行检查 |
| --- | --- |
| 接近 | 读入当前画面，确认目标杯和托盘，检查动作的可达范围 |
| 夹持 | 根据图像、本体或接触反馈确认夹住，再进入抬升 |
| 搬运与放置 | 检查托盘位置和杯子携带状态，释放后验证杯子仍在指定托盘内 |
| 异常恢复 | 观测过期、夹持失败或触发安全限制时，由执行系统停止或重新获取状态 |

推理耗时应连同采集、传输和命令生效时间一起测量。底层限位、碰撞监督和停止机制由系统实施。长时程任务还需要保存已完成的子目标，例如已经持有杯子时，只重新确认托盘位置即可。相关任务组织见[导航、操作与任务规划](../04_导航操作与任务规划/README.md)。

<a id="evaluation"></a>

## 怎样判断模型到底学会了什么？

| 想验证的能力 | 可以怎样设计对照 |
| --- | --- |
| 遵循指令 | 固定布局，分别指定红杯和蓝杯，或切换左右托盘，记录选错对象与放错位置的次数 |
| 适应视觉变化 | 固定指令，改变杯子初始位置、光照或相机视角，报告各条件成功率 |
| 完成物理操作 | 分别记录选中目标、抓稳、搬运和放稳，区分语义错误和执行错误 |
| 扰动后恢复 | 在受控条件下改变目标状态，统计恢复成功率、时间和人工接管 |
| 跨本体迁移 | 明确目标本体是否参加训练、提供多少示范，以及使用了哪些动作适配 |

报告结果时写明任务限定、试验次数、是否允许重试及是否进行目标本体微调。一次在新场景里抓杯成功只能支撑对应测试条件下的结论。读论文时也应区分零样本执行和少量示范微调后的结果。

## 自检问题

1. 同一个桌面布局下，怎样验证策略确实使用了「左边」这个语言条件？
2. 语言模型识别出了红杯，为什么仍需机器人轨迹来训练动作输出？
3. 离散动作 Token 与连续动作专家对控制接口各有什么要求？
4. 新机器人微调后成功率提高，报告中应补充哪些信息？

<details>
<summary>展开参考答案</summary>

1. 固定场景与起点，只改变指令里的左右目标，检查放置结果能否随指令切换。
2. 语义表征提供目标线索。轨迹把这些线索和具体本体的观测、动作及时间关系连接起来。
3. 离散 Token 需要解码并检查量化精度。连续输出需要恢复单位、参考系和动作时序。两者都需要执行侧验证。
4. 说明目标本体是否曾出现在预训练数据里、微调用了多少示范、哪些模块被适配，以及测试场景与训练场景如何划分。

</details>
