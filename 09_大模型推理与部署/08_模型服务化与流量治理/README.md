# 08. 模型服务化与流量治理

> 推理引擎负责把请求算出来，服务化系统负责让请求在真实流量下可进入、可控制、可恢复。

## 本章定位

本章建立 API、路由、准入、排队、超时、重试、多租户和扩缩容的基本关系，不展开通用微服务或 Kubernetes 教程。

## 核心链路

```text
Client
  → Gateway：认证、限流、协议
  → Admission / Queue：准入、排队、背压
  → Router：模型、版本与副本选择
  → Inference Replica：执行与流式返回
  → Metrics / Logs / Traces：观测与治理
```

## 1. API 与流式响应

服务层需要定义输入格式、采样参数、错误码、超时和流式协议。兼容同一种 API 只表示调用方式相似，不代表模型能力、性能和扩展功能相同。

流式响应可以降低用户感知等待时间，但会带来长连接、取消传播、中途错误和客户端断开等额外状态。

## 2. 路由

路由器可能按以下条件选择目标：

- 模型、版本、量化或 LoRA Adapter；
- 副本负载、队列长度和健康状态；
- GPU 类型、显存容量和部署位置；
- 租户、优先级、地域和数据边界；
- Prefix Cache 命中机会或会话粘性。

简单轮询不一定适合推理服务，因为不同请求长度、缓存状态和副本负载可能差异很大。

## 3. 准入、排队与背压

系统容量有限时，必须决定请求是立即进入、排队、降级还是拒绝。

| 机制 | 作用 | 风险 |
| --- | --- | --- |
| Admission Control | 防止超出显存、队列或 SLO 容量 | 规则过严会浪费资源 |
| Queue | 吸收短时流量波动 | 无界队列会把过载变成长延迟 |
| Rate Limit | 控制用户或租户请求速率 | 需要公平策略和准确配额 |
| Backpressure | 将下游压力反馈给上游 | 上游必须能够减速或失败返回 |

排队不是免费的容量。队列持续增长通常表示输入速率已经超过有效服务能力。

## 4. 超时、取消、重试与熔断

- **超时**：限制请求最长等待或执行时间。
- **取消**：客户端停止后尽快释放队列、KV Cache 和执行槽位。
- **重试**：处理暂时性失败，但可能制造重复负载。
- **熔断**：故障或过载时暂时阻止更多请求进入。
- **降级**：切换更小模型、缩短输出或关闭非必要功能。

生成请求成本高且执行时间长，盲目自动重试可能加重故障。重试前要判断请求是否幂等、服务是否已过载以及前一次执行是否仍在运行。

## 5. 多租户与隔离

多租户服务需要处理配额、优先级、资源隔离、数据边界和成本归属。只按请求数量限额可能不公平，因为长上下文和长输出消耗的 Token、显存和时间更多。

更合理的治理通常结合请求数、Token 数、并发、队列时间和预算。

## 6. 发布与扩缩容

| 能力 | 主要目的 |
| --- | --- |
| Readiness / Health Check | 区分正在加载、可服务和故障副本 |
| Rolling / Canary | 控制版本升级和回滚风险 |
| Replica Scaling | 扩展请求容量与可用性 |
| Model Loading Strategy | 控制冷启动、权重下载和显存初始化 |

GPU 利用率不是唯一扩缩容信号。推理服务还应观察请求率、队列、TTFT、Goodput、KV Cache 使用率和冷启动时间。

## 常见误区

- **队列越长，吞吐越高。** 长队列通常只会恶化等待和超时。
- **重试可以提高所有请求成功率。** 过载时重试可能触发重试风暴。
- **增加副本就能线性扩容。** 模型加载、路由、共享存储和 GPU 供给可能成为瓶颈。
- **GPU 利用率低就应该缩容。** 请求可能受显存、延迟 SLO 或间歇流量约束。
